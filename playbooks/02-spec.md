# Playbook 02 — Spec

Цель: из `docs/intake.md` написать формальную спеку проекта в `docs/spec.md`.

## Когда запускается
- После `playbook 01-intake.md` завершён.
- Вручную: `/spec` или после редактирования intake.

## Skill
`superpowers:writing-plans` (часть про spec)

## Структура `docs/spec.md`

```markdown
# Spec — <название проекта>
Дата: <YYYY-MM-DD>
Статус: draft

## 1. Цель
<2-3 предложения. Что строим, для кого, какую боль закрывает.>

## 2. Не цели
<что НЕ делаем в этой итерации>

## 3. Главные сценарии
### Сценарий 1: <название>
1. Пользователь открывает X.
2. Видит Y.
3. Жмёт Z.
4. Получает W.

(3-5 сценариев)

## 4. Сущности и схема данных
### User
- id, email, role, created_at
- relations: User has many Projects

### Project
- id, owner_id, title, status, ...

(все сущности с атрибутами и связями)

## 5. API endpoints (high-level)
- POST /auth/login
- GET /projects
- POST /projects
- ...
(детальные контракты — на шаге /contracts)

## 6. Внешние интеграции
- Stripe: ...
- Supabase Auth: ...

## 7. Acceptance criteria
- [ ] ...
- [ ] ...

## 8. Риски
- Risk: ...
  Mitigation: ...

## 9. Открытые вопросы
- ...
```

## Качество спеки

- **Каждый сценарий** проверяем: «А что если ошибка на шаге 3?». Если непонятно — спроси пользователя.
- **Каждая сущность** проверяем: «У неё есть owner? Soft-delete? Versioning?».
- **Acceptance criteria** должны быть тестируемыми («есть API /X» — плохо; «POST /X с валидным payload возвращает 201 и id» — ок).

## После завершения

1. Закоммить `docs/spec.md` (commit: `docs: spec v1`).
2. Скажи человеку: «Спека готова. Прочитай и подтверди. После апрува перейду в декомпозицию.»
3. Жди явного «ок» / «апрув» / «продолжаем».
4. Не запускай `playbook 03` без апрува.
